# Shopify installation and granted scopes

## Current supported path

Carteio is a standalone/API-only SaaS app. It starts the Shopify authorization-code grant from the Carteio dashboard, validates the callback HMAC, timestamp, one-time state and store domain, then exchanges the code for an expiring offline token. Refresh tokens are rotated server-side and encrypted credentials remain attached to the existing tenant-owned connector. Shopify's current guidance assigns authorization-code grant to apps running outside the Shopify admin; token exchange is for apps running inside the admin. Carteio must not adopt App Bridge or token exchange unless its application architecture changes.

Carteio is a standalone/API-only app. Its supported flow is Shopify's authorization-code grant, not embedded App Bridge authentication or token exchange. The authorization URL continues to include the explicit `scope` parameter; Shopify's documentation says standalone apps use the authorization-code grant and request later scopes by redirecting again with an updated list. Dev Dashboard scopes are not exposed to this backend as a runtime list. Shopify separately documents an optional-scope URL for scopes declared as `optional_scopes`; the currently configured legacy flow has not been verified as using that mechanism, so Carteio does not emit that URL or assume optional-scope semantics.

`SHOPIFY_SCOPES` remains the compatibility request list for a new/legacy install (currently the three base read scopes). For a connected store, the explicit owner/admin **Request Shopify permissions** action uses the typed `SHOPIFY_SCOPE_UPGRADE_SCOPES` allow-list in [`shopify-scope-upgrade.config.ts`](../../backend/src/config/shopify-scope-upgrade.config.ts). Populate it only with read-scope handles deliberately selected from the released Dev Dashboard app version. It is empty by default and rejects invalid, duplicate, and `write_` handles; Carteio has no Shopify write operation, so new write scopes cannot be added by this path. On this explicit action, Carteio rechecks current grants once using the stored access token, verifies shop identity, and refreshes the snapshot. The upgrade URL contains only those just-verified existing grants plus the configured upgrade list; `SHOPIFY_SCOPES` does not add new scopes to an existing store's upgrade request. The UI shows that exact union and asks for confirmation before redirecting. The code does not copy the Dev Dashboard declaration automatically or request every declaration by default.

The owner-supplied scope inventory lives in [`shopify-scope-inventory.config.ts`](../../backend/src/config/shopify-scope-inventory.config.ts). It is displayed as an inventory, not as an app-version declaration or grant. Admin API handles use the legacy Admin OAuth request path only; `customer_*` Customer Account API scopes and `unauthenticated_*` Storefront API scopes are not sent in that request. The inventory is API-family/access/risk classified, but only scopes confirmed in Shopify's `2026-10` scope reference receive that documentation status; this still does not establish app-version declaration or grant. Only the existing product, price, category, inventory, order, and fulfillment mappings are treated as Carteio operations, and every other supplied scope remains non-executable until an API implementation is registered.

The callback reuses the existing one-time workspace/user/store-bound state, callback HMAC and timestamp verification, domain validation, authorization-code exchange, expiring offline tokens and encrypted vault. Upgrade state carries a hash of the configured list, so config changes abort before token exchange. For an existing connected store, callback discovery validates `currentAppInstallation.accessScopes`, verifies that every previously granted scope is retained, verifies the returned shop identity, then conditionally updates the encrypted credential using the previously observed ciphertext and the verified scope snapshot in one transaction. A declined added scope is recorded as absent in Shopify's verified snapshot; it does not fail the upgrade if prior grants remain intact. A concurrent callback cannot overwrite a newer credential. The callback does not cancel sync jobs, change connection state, clear provider capabilities, alter webhook identity, or touch permissions and synced data. If prior grants are missing or identity differs, database state is left unchanged.

Shopify retires other expiring offline refresh tokens when a new authorization-code token is acquired. Thus the stored old token is not overwritten before verification, but Shopify may retire its old refresh token earlier in the callback lifecycle; if verification fails, the old encrypted token remains stored and may be usable only until its existing access-token expiry. This provider behavior cannot be made transactional with Carteio's database. A real development-store rehearsal is required before enabling upgrade config for production merchants. Do not start an upgrade until the app version is released with every requested scope and Shopify has approved any protected-customer-data access.

Shopify also supports app-version scope configuration in Dev Dashboard. Its docs say Dev Dashboard-created apps declare scopes in a released app version, while an app implementing authorization-code grant itself supplies the `scope` parameter; adding scopes requires a new app version and merchant approval, and the authorization-code flow must be run again with the updated scope list. Shopify-managed installation describes Shopify handling installation/scope changes from app configuration, but the same docs state standalone apps should use authorization-code grant. These descriptions do not establish that Carteio can replace its URL parameter with an app-version lookup or omit it. The exact live app behavior must be proven in a development store before changing runtime requests.

The repository contains no supported endpoint or credential for reading a Dev Dashboard app version's declared scopes at runtime. No such endpoint is assumed here. Shopify's current standalone-app guide explicitly requires a comma-separated `scope` list in the authorization URL. This is why the released app version's 50+ configured declarations do not by themselves replace Carteio's current request list while its manual authorization-code flow remains active. Keep the compatibility request list unchanged until a supported installation-mode transition is validated; do not claim app-version declarations as verified merchant grants.

Shopify documents two relevant safe paths: retain authorization-code grant and send an explicit scope list during owner/admin initiated authorization, or migrate installation/scope management to Shopify-managed installation. Shopify's documented legacy-to-managed migration guide is tied to Shopify CLI configuration and removes OAuth callback routes for installation/scope updates; it is not a drop-in for this standalone NestJS OAuth implementation. No Dev Dashboard-only runtime scope enumeration path was found in the official documentation. Therefore this repository does not switch modes automatically. A Dev Dashboard-managed installation conversion requires a confirmed supported setup for the current standalone app, development-store validation, and an explicit code migration before release.

Shopify documents required and optional scopes. Optional scopes must be declared before an app requests them dynamically, and a merchant may grant or decline the request. Do not request arbitrary undeclared scopes, and do not infer approval from the app-version configuration. The optional-scope request URL documented by Shopify is a separate mechanism from the current authorization-code `scope` parameter; its compatibility and callback behavior must be verified for this exact app before implementation.

## Actual grant and permission source

The only actual-grant source is Shopify's authenticated Admin GraphQL `currentAppInstallation.accessScopes { handle description }` response, obtained with the token for the store bound to the verified tenant/connector. Carteio persists handles, descriptions and verification time on that store's `IntegrationConnection`. Scope-update webhooks update handles; descriptions are retained from the prior verified metadata when available. Explicit verification can refresh metadata and freshness.

Freshness expires after 24 hours for authorization decisions. A failed refresh preserves the last known snapshot, but stale or unavailable data cannot authorize commerce access. Scope discovery is not performed for visitor chat messages.

The Permissions Dashboard shows verified grants and unknown grants. A missing operation scope is now labeled `UNKNOWN` when it is absent from a fresh snapshot: the app cannot truthfully distinguish “not declared,” “not requested,” or “declined” without authoritative declared-scope metadata and a confirmed request outcome. A stale snapshot remains `STALE`. No requested-scope environment value is used to establish actual grants or make that classification.

Unknown grants remain visible and have no operation mapping. A grant alone does not make an operation executable: the operation must be registered by Carteio, provider capability verified, snapshot fresh, workspace permission enabled, and (for AI) the selected assistant permission enabled. Shopify write scopes do not create AI mutation tools. Orders remain restricted; customer-sensitive fields and public customer-specific order access require separate verified authorization/ownership.

## Existing stores and migration boundary

Existing connections are untouched until an owner/admin starts the explicit scope-upgrade route. The callback updates credentials and verified scope snapshots only after Shopify authorization and grant verification; it preserves connection state, organization and assistant ownership, product/variant history, provider capabilities, permissions, webhook identity, and sync jobs. No automatic authorization or data sync is started.

Do not remove `SHOPIFY_SCOPES`: the existing install path still uses it. The typed upgrade allow-list is empty by default and is used only after an owner/admin invokes the upgrade flow. Roll back by restoring that allow-list to empty and withholding the action in a later code release; existing installations and the legacy install route remain unchanged. Never reverse or clear already persisted grants, credentials, permissions, or sync data as part of rollback.

### Separate managed-installation conversion

The current change deliberately keeps `use_legacy_install_flow=true` and authorization-code OAuth. Converting the standalone app to Shopify-managed installation is a distinct architecture migration and is not required for this explicit scope-upgrade flow. Do not remove `SHOPIFY_SCOPES` unless a later, separately validated flow removes every runtime use of its installation request path.

Before enabling the allow-list: compare each selected handle with the active released Dev Dashboard version, populate the typed config, deploy the backend code/config, rehearse on a development store, inspect the merchant approval screen, then confirm the actual grant snapshot in Carteio after the merchant approves or declines. Do not request the full declared list by default, add write scopes, or claim a scope is granted before Shopify returns it in `currentAppInstallation.accessScopes`.
