# Phase 08A indexing audit

The prior local Ollama embedding option was removed from the application runtime because the product policy disallows a local AI server. Groq chat credentials are not treated as an embedding capability. PostgreSQL lexical indexing is the default and works without any embedding provider. Optional semantic indexing is explicitly gated on the OpenAI embedding endpoint, model, opt-in flag, and API key.

The optional `text-embedding-3-small` profile is 1536 dimensions. Existing physical vector storage is 1536 dimensions; no new zero-padding profile is used. OpenAI requests are not made unless semantic indexing is explicitly enabled. The lexical worker still publishes a searchable generation when embeddings are unavailable or fail, and records semantic status separately. Search previews disclose whether results came from lexical-only or hybrid retrieval.

The additive Phase 08 lexical migration alters the Phase 08A profile constraint while retaining historical chunk rows. It narrows the OpenAI HNSW index to the supported `text-embedding-3-small` model. Historical BGE-M3 chunks, if any, are retained but are not produced or queried by the current runtime. The database's true migration state was not verified: the read-only `prisma migrate status` command stalled before returning. No migrations were applied, and neither earlier migration was edited.

Lexical retrieval uses PostgreSQL's `simple` text-search configuration, phrase matching and title matching. Unicode is preserved, but lexical matching is token-based and does not establish English↔Hindi or Hinglish semantic equivalence. Cross-language retrieval quality is unverified and must not be claimed.

## Website learning quality audit and Noupe benchmark plan (2026-10-17)

### Scope and confidence

This is a code-level audit of the current repository. No merchant site was crawled, no database was queried, no Noupe account was used, and no model/API call or test suite was run. Noupe is treated as a black-box comparison target; this report makes no claim about its internal algorithms. Since the merchant domain was not supplied with this audit request, the controlled comparison remains pending selection of one public test domain and approval to run the external sessions.

The source proves what Carteio is configured to do. It does not prove that a particular deployment has its processing worker enabled, that a source is assigned to the assistant, that a crawl completed, that embeddings exist, or that the configured provider/model supports the expected quality. Those require deployment diagnostics and an authorized run against real data.

### Current source-to-answer path

1. An owner/admin registers a website using `KnowledgeService.createWebsite`; the URL is normalized and the source, one initial CRAWL job, and a sync-run record are created transactionally. Subsequent refreshes are manual by default. The worker is separately gated by `KNOWLEDGE_WORKER_ENABLED`.
2. `WebsiteCrawler.crawl` starts from the URL, reads same-host `robots.txt`, the conventional `/sitemap.xml`, and at most ten sitemap hints. Sitemap indexes are followed to depth two, with sitemap and URL bounds. It also discovers anchors from fetched HTML and orders likely About/FAQ/policy pages ahead of generic paths. It only accepts the exact starting hostname and configured path prefix. A crawl is bounded by the configured page/depth limits (Prisma defaults: 50 pages and depth 3), a 120-second job budget, a 15 MB total transfer limit, 1.5 MB per response, per-host pacing, and redirect limits. A sitemap-backed run is considered complete only if discovery was not truncated and the queue finished without robots skips, fetch failures, unsupported pages, or retryable failures.
3. HTTP destinations and redirects are DNS-resolved and pinned to public addresses. The crawler does not follow off-host redirects. It respects parsed robots directives and fails closed on robots 401/403 and temporary inability to check robots. These controls protect the crawler but also mean blocked, login-only, CAPTCHA-protected, or otherwise restricted pages are intentionally not available.
4. HTML extraction uses parse5 and visible text, preferring `main`/`article` when present; it removes navigation, headers/footers, forms, scripts, hidden nodes, and common noise. It preserves title, canonical URL (only when same-host), language, content hash, timestamps and a URL/title-derived page category. It extracts FAQ question/answer pairs from FAQPage-style JSON-LD. It does not currently build normalized website Product, Organization, Offer, ImageObject, or collection records from JSON-LD/Open Graph/markup. Images, alt text, product options, variants, product IDs, exact prices/currencies and stock are not retained as a typed website-product projection. Product text visible in ordinary HTML may be indexed, but exact fact coverage depends on what text is visibly rendered.
5. JavaScript rendering is an isolated, optional Linux/gVisor container configured by deployment. It is attempted only when static HTML extraction returns no useful page. Therefore a static shell with enough text to pass extraction, but missing hydrated product/list content, can suppress rendering and be stored as a successful-looking, incomplete page. If rendering is unavailable, the run reports a bounded renderer error; the implementation does not bypass bot controls.
6. Website pages are stored in `KnowledgePage`; chunks are stored in `KnowledgeChunk` and tagged with source/page, version, generation, locator, hash and optional vector metadata. `chunkKnowledgeText` preserves Unicode, uses a 2,800-character default with 240-character overlap, and heuristically treats short lines as headings. The crawler removes repeated identical chunk bodies across the entire crawl generation, so repeated boilerplate is reduced but an identical fact repeated on different pages may only be associated with the first page's chunk. Unchanged pages and matching chunks can reuse prior content/embeddings. Partial crawls can publish pages with `SUCCEEDED_WITH_WARNINGS`, and source-wide removal reconciliation is restricted to authoritative complete crawls.
7. PostgreSQL `simple` lexical search uses websearch/phrase queries over chunk text and source title. Optional OpenAI `text-embedding-3-small` embeddings enable semantic search; when absent or unavailable, the system deliberately falls back to lexical-only search. Semantic and lexical lists are merged by reciprocal-rank fusion, not a learned cross-encoder reranker. The hybrid path does not by itself guarantee English/Hindi/Hinglish equivalence; lexical token search is language-sensitive, while semantic coverage depends on the embedding profile and actual indexed vectors.
8. Public retrieval is restricted to active, public, ready, assigned sources and current assistant/domain authorization. Search returns only a bounded number of results (normally five, three for product intent); lexical candidates are pre-limited, semantic results are separately bounded, and hybrid results are merged. The answer context selects at most five items, with at most two per source by default, up to 32 KB. Knowledge excerpts passed onward are cut to 1,600 characters. This is an intentional safety/cost bound, but can omit a relevant section, a long condition, or a lower-ranked corroborating source.
9. The conversation interpreter and answer generator use the configured provider/model. Recent authorized turns are bounded; context resolution and model-generated query variants can support follow-ups and multilingual queries, but are not a guarantee. The actual agent tool manifest currently exposes only `search_business_knowledge` and (when eligible) `search_store_products`, each bounded. Product search is backed by Shopify commerce records, not by structured products extracted from the website. A website-only merchant therefore has no equivalent structured catalog tool for product attributes, images, variants or broad product browsing.
10. Before returning a sourced answer, evidence is revalidated against current source/version/hash/assignment and citation IDs are checked. The plan explicitly records `entailmentVerified: false`. The response check requires at least one supplied citation, rejects unknown citations and screens numeric strings against evidence text; it does not establish that every nonnumeric factual sentence is entailed by the cited excerpt. Thus a correctly cited but semantically unsupported claim can pass the deterministic check. This is a concrete response-validation limitation, not a claim that a specific answer was wrong.

### Code-supported likely quality-gap causes

These are priority hypotheses to verify against actual pages and transcripts, ordered by their likely impact. They are not an attribution of a Noupe result without a controlled run.

1. **Website products are text-only.** No structured website-product projection is produced by the crawler. Product listings may yield thin or repeated HTML text; image URLs, alt text, product identifiers, options, variants and price/currency facts in structured markup are not captured as typed fields. Shopify catalog data can compensate only when a Shopify connector is connected, scopes and merchant/assistant permissions allow it, and product records have actually been synchronized.
2. **Hydrated content can be missed.** Rendering is fallback-only after static extraction fails its useful-text threshold. A page can pass that threshold from static navigation or a generic shell while its important JavaScript content is absent. This is especially material for collection grids, search pages, and client-rendered product details.
3. **Discovery is intentionally bounded.** The defaults are 50 pages and depth 3. Sitemap recursion is bounded, URL discovery can be truncated, the crawler is same-host only, and only anchors, sitemaps, and eligible authorized Shopify page seeds are considered. Very large, deeply nested, app-driven, locale-hosted, or poorly linked sites may have low coverage. A source can still have useful saved pages while the overall crawl is incomplete or warning-marked.
4. **Fact structure is mostly lost.** General HTML text is flattened. FAQPage JSON-LD is the notable structured extraction; product/offer/organization/contact schema, tables, image galleries, option selectors and conditional purchase/shipping UI do not have dedicated parsers. Page category is inferred from path and title rather than validated content classification.
5. **Retrieval has bounded top-k and no learned reranker.** `simple` lexical matching is weak for paraphrases and cross-language queries. Semantic search is optional and has no fallback provider in this indexing profile. RRF combines ranks but cannot repair missing pages or absent facts. Top-k, per-source caps, a 1,600-character excerpt limit and five-item context budget can remove relevant evidence after retrieval.
6. **Grounding validation is citation-level rather than entailment-level.** Citations prove that a supplied reference was named, not that each claim follows from it. Numeric checking is a string-presence check; it is not unit/condition/claim parsing. Conflicting values are detected heuristically in limited cases, and condition parsing is explicitly absent. This leaves residual unsupported-claim and contradiction risk even when the correct evidence was crawled and retrieved.
7. **Readiness is not the same as completeness.** `READY` indicates a published searchable generation, not that all important pages or product facts were discovered. The sync records expose discovered/changed/unchanged/failed/skipped counts and a warning state, but a useful readiness badge alone should not be used as a quality metric. Deployment worker state, source assignment, website-domain authorization, embedding state, and the crawl's completeness flag must be recorded separately in the benchmark.

### Controlled Noupe vs Carteio black-box benchmark

Run only after selecting a domain the owner is authorized to test and approving external sessions. Use the exact same public URL, page snapshot window, questions, language, device/browser conditions, and comparable fresh-session state. Do not assume or attempt to inspect either vendor's private index, prompts, APIs, or implementation. For Carteio, record the configured provider/model, source version, crawl/index run, assistant assignment, embedding mode, and source freshness. For both products, use a fresh session for independent questions and fresh parallel sessions for each multi-turn script. Avoid training/configuration changes between the two runs. Capture visible answers and timestamps only; redact visitor/customer data.

Before querying, create a human-verified ground-truth manifest from the same public pages: canonical URL, page title, extraction-relevant fact spans, fact type, exact product/options/price/currency/condition, policy qualifiers, and observation time. Do not treat either assistant's answer as ground truth. Pre-register the following 30 questions; replace bracketed entities once from the chosen site's real visible inventory and use the identical substitutions for both assistants:

| # | Question | Evidence to check |

If a fact is absent from the site, mark that subquestion as **unanswerable from the chosen source** before running either system; score a confident invented claim as unsupported, not as correct.

### Measures and attribution protocol

- **Website content coverage:** relevant ground-truth pages saved / relevant public pages in the pre-registered manifest; separately report product detail, collection, FAQ, policy, contact and about categories. Also report sitemap coverage, discovered URLs, saved pages, excluded robots pages, failed/unsupported pages, truncation and complete/warning status. A page count alone is not coverage.
- **Retrieval recall@k and relevance:** for each Carteio question, save the authorized top-k evidence identifiers, URLs, excerpt and score before LLM assembly (with private content stored only in an approved test environment). Blind reviewers mark whether the expected fact span is present, whether top results are relevant, and whether an irrelevant result outranks it. Report recall@1/3/5 and a blinded nDCG@5. Noupe internals are unavailable; compare its visible answer evidence/citations only if it exposes them, otherwise do not claim direct retrieval recall for Noupe.
- **Grounded correctness:** split answers into atomic factual claims. Review each against the pre-registered ground truth and applicable qualifiers; score correct, partially correct, unsupported, contradicted, or appropriately unknown. Report claim-weighted correctness and unsupported factual claim rate (unsupported claims / all factual claims). Two independent reviewers adjudicate disagreements.
- **Context retention:** score referent resolution and retained policy/product details in the two-turn cases; record whether follow-up facts refer to the intended product/policy, not just whether the answer sounds fluent.
- **Freshness:** record source crawl/index completion, page `fetchedAt`, source `lastSuccessfulSyncAt`, and run start/finish; compare answers against the pre-run public snapshot. Report crawl-to-index lag and stale/mismatched fact rate. Do not characterize a public website price as real-time.
- **Latency:** measure user-visible wall time per response at the same client/network conditions, with provider/model and warm/cold session state documented. Report median, P95, and timeout/error rate. Do not compare a preloaded index to a just-started crawl as equivalent conditions.

For every incorrect Carteio answer, trace a single failure chain with these checkpoints and assign the earliest failing stage: **crawl/discovery** (expected URL absent); **extraction** (page saved but fact absent/distorted); **knowledge storage/indexing** (fact present in saved page but no current searchable chunk/vector); **retrieval** (fact chunk exists but not in authorized top-k); **context assembly** (retrieval contains fact but selected excerpt/evidence sent to model omits or truncates it); **LLM reasoning** (complete correct evidence reaches model but claim is wrong); **response validation** (unsupported claim/citation/contradiction passes safeguards or a valid answer is unnecessarily rejected). Preserve request/run IDs, source version/hash, top-k evidence IDs, model/provider, latency and validator outcome so that an answer can be attributed without retaining unnecessary personal data.

### Findings versus conclusions

The source-level audit confirms a website-only assistant can index plain HTML content without Shopify, with optional isolated rendering and optional semantic vectors. It also confirms material limitations in structured product extraction, conditional JavaScript rendering, bounded crawl coverage, language-sensitive lexical fallback, small evidence budgets, and non-entailment response checks. These provide concrete and testable explanations for less useful answers than a competitor that may provide broader/deeper extraction or retrieval. **They do not establish that Noupe actually uses any particular technique or that any one limitation caused a real answer difference.** That causal conclusion requires the controlled benchmark above and stage-by-stage Carteio evidence capture.

### Recommended quality-gap closure order

1. Add site-level coverage and progress reporting that distinguishes sitemap completeness, discovery truncation, rendered-vs-static extraction, category counts, saved/indexed counts, embedding availability, and per-page failures. Do not call a bounded partial crawl complete or AI-ready merely because some chunks were published.
2. Add typed extraction of public Product/Offer/Organization/FAQ structured data and safe HTML/Open Graph image/variant metadata into source-scoped website records or typed page metadata, preserving provenance/confidence/time. Do not overwrite Shopify API records, infer stock quantities, or treat scraped price as live. Add migrations only after proving existing JSON metadata cannot satisfy the contract.
3. Improve page selection with safe category-aware sitemap/link discovery, explicit continuation/resume, and configurable owner-visible budgets. Preserve robots, exact same-host/SSRF controls and partial-snapshot deletion protections. Report category coverage instead of silently treating a capped crawl as complete.
4. Evaluate static-vs-rendered completeness, not only whether static extraction found any text. When page type signals product/collection and critical fields are absent, attempt the existing isolated renderer within the same hard bounds, then merge rendered facts without duplicate pages. If the isolated renderer is not deployed, show this as a blocker/limitation.
5. Build a benchmark set and evaluation harness using the questions above, labelled source spans, multilingual paraphrases, and adversarial/ambiguous but evidence-checkable cases. Tune retrieval only against that set. Report lexical-only and hybrid cohorts separately; add a cross-encoder only if evaluation proves a gain and its latency/cost is approved.
6. Improve claim-level grounding validation, including evidence-to-claim support and conflict/condition handling. Keep deterministic checks for permissions, IDs, dates, numeric values and citations; an LLM judge may be an evaluation signal but must not be the sole runtime safety control.
7. Instrument safe stage metrics (without prompts, page bodies, credentials or visitor text): crawl category coverage/completeness, extraction method, source freshness, retrieval candidate/selected ranks, dropped-for-budget counts, actual evidence bytes, provider/model, validation decision and end-to-end timing. Use them to classify every benchmark miss before changing prompts or model choice.
