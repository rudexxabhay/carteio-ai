# Phase 08 knowledge security

## Website control and outbound requests

Website registration is not crawl authorization. OWNER/ADMIN must create a source-bound DNS TXT challenge and publish the returned token at `_carteio-verify.<hostname>`. The token is random, returned only at challenge creation, stored as a digest, expires in 24 hours, and is cleared on successful atomic verification. Source URL edits and archiving revoke verification. A restored website must be verified again. The same domain can be connected by more than one workspace only through separate DNS proofs; domain ownership is not treated as globally exclusive.

The crawler permits HTTP/HTTPS on standard ports, rejects credentials, zone IDs, internal host suffixes, non-FQDN hostnames, private/reserved addresses and mixed DNS answers. It resolves immediately before every connection, pins the selected validated address, preserves TLS hostname/certificate checks, ignores proxy environment variables, disables automatic redirects, and revalidates each redirect and destination. Crawl requests have bounded size/time/count and same registered hostname/path scope. PostgreSQL reservations pace requests to a hostname across worker processes; advisory/row locking caps global active jobs and allows one active job per workspace. Retain network egress controls as defense in depth. Login/account/payment/order paths are excluded. No site cookies or workspace credentials are sent.

`parse5` performs standards-aware HTML parsing without executing page scripts. Input bytes and DOM node count are bounded. Extraction prefers main/article content and excludes common noisy or hidden elements; site-specific noise can still be missed. Robots rules support wildcard/end-anchor matching and longest-match Allow precedence; nonstandard extensions are not implemented. Sitemap input is bounded and every page URL is still scope-checked.

Phase 08E rendering remains disabled until a deployment administrator supplies a reviewed local image and a Linux Docker runtime backed by gVisor with external networking disabled. The adapter checks Docker runtime configuration and container isolation settings before start: network none, read-only filesystem, no host mounts, non-root user, no added capabilities, no new privileges, private IPC, fixed entrypoint and bounded CPU/memory/processes. The browser explicitly enables Chromium sandboxing, blocks service workers and WebSockets, cancels downloads, dismisses dialogs and uses no session/profile/credentials. Request interception is an additional policy control; it is not the isolation boundary. gVisor and network-none must deny bypass attempts from page scripts, browser workers and native browser code.

The trusted stdio broker permits GET only, exact verified hostname, permitted paths and robots rules; every connection resolves/checks all addresses and pins its destination. Redirects are independently checked and their response streams closed immediately. No Set-Cookie or authorization headers are forwarded. Archive/delete/version/lease authority is checked during processing and before atomic publication; the browser is cancelled on revocation. Unexpected protocol output, resource exhaustion, missing runtime proof or cleanup failure is a failure. Untrusted browser stderr is drained without retaining page logs. No browser ports are exposed.

The Docker daemon/runtime and reviewed image are trusted administrative components. Docker access grants significant host authority: deploy this adapter on a dedicated worker machine or similarly restricted worker deployment, with no application secrets mounted or passed to its containers. Native Windows and ordinary Docker Desktop without the required runtime cannot activate rendering. No unrestricted Playwright mode exists. Actual OS-level containment, runtime/browser compatibility and escape probes have not been tested here. See [deployment checks](phase-08e-rendering.md).

## Tenant and audience checks

Every manager mutation derives the organization from the authenticated workspace membership, and mutation routes use the existing session/CSRF middleware. Page/chunk/search SQL includes tenant and effective-source filters with parameterized values. Effective sources combine direct links and active linked bases and are deduplicated. Archived sources and inactive assistants are excluded.

Manager preview requires OWNER/ADMIN and may return restricted source excerpts. Public visitor policy is separate: the internal policy hook requires an active assistant, an active verified website, exact HTTPS host binding, assistant-effective eligibility, and `PUBLIC_REFERENCE`. There is no anonymous retrieval endpoint in this phase. The policy hook is not an end-to-end widget security test.

Source text is untrusted reference data. It is not interpreted by the crawler, worker, SQL layer, or authorization service. Phase 09 must keep retrieved content below system policy and must separately validate any tool authorization.

## Lifecycle

Archive immediately cancels pending jobs, pauses website sync, and causes retrieval eligibility checks to fail. Restore preserves visibility; websites return unverified and paused. OWNER-only permanent deletion records a metadata-only audit summary, cancels jobs, then deletes the source. Composite tenant FKs and source-owned cascades remove that source's pages, chunks, jobs, sync history, memberships, and direct links without touching unrelated sources. There are no managed external files in Phase 08.

## Verification limits

Earlier Jest attempts stalled. Phase 08E supplies a bounded Node test suite that exercises the actual fallback, request policy, pinned-fetch path with controlled DNS/HTTP transports, stdio broker, Playwright hooks with a fake browser, sync provenance and generation publication with a fake database. Backend/frontend TypeScript checks and renderer syntax checks are also run directly without scripts that generate Prisma Client. These checks do not launch Chromium, exercise a real network server, demonstrate a kernel isolation boundary or execute Neon SQL. Browser, containment, migration, retrieval and UI end-to-end verification remain manual prerequisites.
