# Phase 09D.7 evaluation engine

The offline evaluation contract lives in `backend/src/modules/workspaces/intelligence-evaluation.ts`; synthetic, versioned examples live in `intelligence-evaluation-datasets.ts`. Cases are schema validated and dataset IDs must be unique. The explicit runner bounds case count, observes cancellation, returns blocked outcomes on executor failure, and does not import or call a provider. A future caller must supply and separately authorize any executor.

The deterministic checks reuse the production multilingual interpretation validator, exact-span scope split validator, and provider/model route validation. They check observed citation IDs against an explicitly supplied authorized set, provider provenance consistency, exact identifiers, bounded user-turn offsets, server-owned limitations, forbidden source categories, and claims to perform live work. These checks establish contract properties only. A valid reference ID does not show that a statement is entailed by its source; semantic interpretation, response naturalness, tone, cross-language quality, contradiction resolution, and entailment need a separately labeled mocked, authorized live, or human-reviewed evaluation.

The v1 fixture set covers all 16 layers, English/Hindi/Romanized Hindi/Hinglish and code-switching, and synthetic e-commerce, logistics, SaaS, healthcare, finance, education, real-estate, and general support scenarios. It includes injection, fake system/admin instructions, cross-tenant and cross-session attempts, provider switching, exfiltration URLs, fake API claims, unsupported personal assertions, false citations, and mixed-scope requests. Fixtures state interpretation ground truth; they never grant tenant permissions or live capability.

Results preserve PASS, FAIL, NOT_EVALUATED, INCONCLUSIVE, BLOCKED, and REQUIRES_HUMAN_REVIEW. Unknown or absent observations do not pass. Aggregates retain status counts and require a nonzero denominator. A deterministic release gate requires at least one deterministic/adversarial case, every such case passing, and no critical/high failure. Live multilingual readiness is reported separately and remains NOT_EVALUATED without live cases. These gates describe evaluated results; they do not change runtime guards.

Safe reports include allowlisted case IDs, layer, method, status, check category/code, severity, aggregate metrics, tenant ID, dataset version, and caller-supplied timestamp. They omit messages, prompts, evidence, private conversation content, and credentials. The report builder refuses a tenant mismatch, and the diagnostics visibility predicate requires an enabled flag plus OWNER/ADMIN role and matching tenant. No route, persistence, dashboard, or normal-conversation integration is added; owner-facing integration should use authenticated tenant context and current membership/role checks before exposing a report.

No live provider request, external evaluation, test runner, scheduled job, or production state mutation is part of this phase. Jest tests are authored but deliberately not run. Quality scores are unavailable unless an actual result has an adequate observed denominator; mocked and live provider methods remain visible as distinct labels.
