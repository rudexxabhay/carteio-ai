# Carteio Natural Conversation Engine

## Summary

The Testing chat already uses the shared `ConversationOrchestrator` path. It performs one model interpretation call, then chooses between a social response, business-scope handling, authorized retrieval/tools, and grounded generation. There is no cached previous “missing knowledge” answer that is replayed for every new message.

The source explains how the reported repetition can occur, but it does not contain the runtime interpretation output for the turns in question. If the interpretation model does not recognize a short acknowledgment or feedback as conversational, the turn continues into normal business routing. If retrieval then has no matching evidence (or generated business output is rejected during grounding), `generateNoEvidenceReply()` runs again with the old unanswered topic and recent turns in its context. The model can therefore produce another uncertainty explanation. The specific runtime classification cannot be confirmed from the available source alone.

A second confirmed weakness was that a validated semantic `ACKNOWLEDGMENT` could be vetoed by a contradictory legacy `intent` field. The semantic classification is now authoritative for a pure acknowledgment after it has passed the existing checks for uncertainty, mixed business intents, entities, and unsafe instruction content. The interpretation prompt also explicitly prioritizes the current turn over unresolved prior intent and calls out informal spelling, shorthand, transliteration, and typos. No new model call was added.

## Current Testing chat execution path

1. `PlaygroundChat` sends the current text through `sendPlaygroundMessage()` to `POST /:assistantId/playground/chat`.
2. `AssistantController.playgroundChat()` passes the authenticated user, workspace, assistant, request ID, and cancellation signal to `AssistantService.playgroundChat()`.
3. `AssistantService` delegates to `ConversationOrchestrator.playgroundChat()`.
4. The orchestrator checks workspace membership, assistant ownership and active status, resolves an owned Playground session, and loads bounded recent history.
5. `executeSharedAI()` calls the configured provider once for semantic interpretation. The prompt asks it to classify the latest conversational act, language/script, intent, context, and retrieval need.
6. A validated standalone social act or conversation feedback is sent to the configured provider for a short model-written response and returns before knowledge retrieval.
7. Other turns continue through business-scope decisions, authorized Knowledge Base resolution and retrieval, permitted tools, prompt assembly, generation, response checks, and persistence.
8. Widget turns reach the same `executeSharedAI()` through `SaasService.recordCustomerMessage()` after `WidgetService` has validated the visitor session. The widget keeps its separate origin/session authorization.

The Testing modal is the Playground UI, not a separate retrieval implementation. Its route and provider/model metadata are visible in `frontend/src/pages/training/PlaygroundChat.tsx` and the Playground API client.

## Cause and response-selection findings

- A new message is not simply replaying a stored fallback. Replay is limited to the same idempotent client turn; separate messages go through interpretation again.
- Normal social classification is model-driven. `decideSocialResponse()` requires a confident semantic classification, matching semantic intent, no entities, and no mixed business request. Previously it also required the legacy intent label to match. That legacy field could carry an old `business` label and force a pure semantic acknowledgment back into Knowledge routing. This gate is corrected for acknowledgments only.
- The interpretation prompt now states that the latest message controls the current act. Unanswered prior questions remain context only unless the new turn actually follows up, supplies requested detail, or clearly refers to the business question. It also instructs the interpreter to recognize standalone social turns despite informal spellings and transliteration, and to classify assistant-behavior feedback separately from merchant complaints.
- The no-evidence response is generated by the configured model when available. Its prompt includes the current question and recent turns and asks it not to repeat the prior answer verbatim. It is used only after no evidence/tool route is selected or grounded generation is rejected. Provider failure or invalid output uses a brief fact-free technical fallback.
- The response validator does not replace a validated social response. Grounding checks apply to evidence-bearing business answers; if such an answer fails validation, the current path requests a no-evidence response rather than returning the rejected factual text.

The available source and existing diagnostics do not establish whether the reported individual responses came from the no-evidence generation call or the deterministic technical fallback. For provider-generated responses, persisted `answerOrigin`, provenance, and provider/model metadata are returned to the UI. Deterministic fallbacks are persisted as `KNOWLEDGE_FALLBACK`/system responses and do not receive a false provider attribution. The UI renders provenance and “Generated by …” only when the corresponding response metadata is present.

## Conversation behavior and boundaries

- Social acknowledgments and feedback use the existing interpretation and response-generation route, with bounded prior turns to understand context. They do not trigger Knowledge retrieval or business tools after validated classification.
- Business questions still use the effective workspace Knowledge Base, existing source permissions, retrieval filters, grounding checks, and configured tools.
- Short contextual follow-ups remain business requests when the current turn refers to the previous topic or supplies a requested detail.
- A genuinely missing business fact remains uncertain. The model may phrase that uncertainty naturally, but cannot use social handling to make merchant claims or perform actions.
- Language and script instructions use the same interpretation result and bounded history. Explicit language preference takes priority, followed by the current message and style. No fixed language-to-response table was added.
- Tenant and assistant authorization, widget session/origin validation, source visibility, Shopify permissions, tool authorization, and retention behavior are unchanged.

## Hardcoded responses that remain

There are fixed strings in the existing system for technical/safety situations: provider failure, invalid or unsafe generated output, security/private-data handling, and some social responses when interpretation or social generation is unavailable. `classifyDeterministicSocialMessage()` also supports a limited exact-form acknowledgment fallback when interpretation output is invalid. These are fallback controls, not the normal social response path. The normal validated social and feedback responses are generated by the configured model. This change did not add fixed customer-facing replies or phrase-specific production rules.

## Files changed

- `backend/src/modules/workspaces/conversation-orchestrator.service.ts` — clarified current-turn priority in the existing interpretation prompt and added a metadata-only `conversation_turn_routed` event with safe enum values, request/workspace/assistant IDs, channel, continuity, and bounded history count. No message, prompt, or evidence content is logged.
- `backend/src/modules/workspaces/social-conversation.ts` — a validated pure acknowledgment no longer gets rejected solely because the legacy intent field is stale; other social categories keep their compatibility check. The social path remains fact-free and tool-free.
- `backend/test/assistant.playground.spec.ts` — added deterministic mocked-provider coverage for an acknowledgment after a no-evidence answer with a stale legacy intent; expanded the feedback test to include the prior acknowledgment turn.
- `docs/ai-audit/CARTEIO_NATURAL_CONVERSATION_ENGINE.md` — this report.

## Regression coverage added, not executed

The added Playground regression checks assert that the acknowledgment uses the model, skips Knowledge retrieval, includes prior context, and retains provider attribution even when the legacy intent says `business`. The feedback regression now includes the original unanswered business question, the prior uncertainty answer, and an intervening acknowledgment, then checks that the latest feedback is handled through the model without retrieval.

Existing tests cover model-written social turns, contextual acknowledgment after a successful answer, model-generated uncertainty, and provider-failure fallback. No tests, builds, or external provider calls were run for this change.

## Cost, limitations, and verification

No provider call was added. A normal request still uses the existing interpretation call and, for a social response, its existing generation call. The longer interpretation instructions add a small amount of input-token overhead. The provider may still misclassify informal or ambiguous language; the new metadata event is intended to distinguish that from retrieval, generation, or fallback behavior on a separately approved run.

Manual verification after approval:

1. In the Testing chat, ask a merchant policy question that currently has no indexed evidence.
2. Send a brief standalone acknowledgment in the same session.
3. Send feedback that the assistant is repeating itself.
4. Inspect `conversation_turn_routed` events for the same session’s request IDs. The acknowledgment should route as `SOCIAL_RESPONSE` and the feedback as `CONVERSATIONAL_FEEDBACK`; neither should enter Knowledge retrieval.
5. Confirm both replies are natural model output, and inspect the UI provenance/provider label against the returned metadata.
6. Ask a new business question and a genuine contextual follow-up to confirm they still route through authorized retrieval.
7. Repeat through an authorized widget session only after independently confirming origin and session authorization.

This is a source-level correction with deterministic regression coverage. Naturalness, model classification reliability, and runtime behavior remain unverified until the tests and the manual conversation sequence are run separately.
