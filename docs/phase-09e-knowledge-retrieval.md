# Phase 09E — Knowledge retrieval changes and audit

## Existing architecture

The repository already has a real FAQ/Text ingestion path and PostgreSQL retrieval. `KnowledgeSource` owns workspace, type, visibility, processing state, source version and active index generation. `KnowledgeBase` and its two link tables scope sources to assistants. `KnowledgeChunk` stores content, source identity/version/generation, content hash, locator, index timestamp and optional `vector(1536)` metadata. FAQ and Text processing uses paragraph-aware chunks with a 2,800-character bound and 240-character overlap; FAQ question and answer are indexed together. Websites have page/sync models, but the processing service currently rejects website indexing, so web pages do not participate in this chat retrieval path.

PostgreSQL `simple` full-text search is the baseline lexical path. The optional semantic profile uses OpenAI `text-embedding-3-small` vectors and pgvector cosine distance when explicitly enabled and compatible indexed vectors exist. Semantic-index failure leaves lexical indexing available. Retrieval embeds the first query only, runs bounded lexical and optional semantic searches, merges chunk IDs with reciprocal-rank fusion (60-rank constant), and selects up to the caller limit. This is hybrid retrieval only when compatible semantic rows were returned; otherwise its mode is `lexical_only`. The RRF result is now labeled `hybrid_rrf`, and deterministic chunk-ID tie breaking makes equal fused scores stable. These are ranking mechanics, not measured relevance or recall scores.

Before database search, workspace access and active assistant ownership are checked, then the effective-source resolver supplies only linked FAQ/Text IDs. Search SQL independently constrains organization, those IDs, active assistant, registered/READY source state, current source version and active generation. Public search additionally requires PUBLIC_REFERENCE, non-deleted sources, and an active non-archived Knowledge Base linked to that assistant. Evidence is batch revalidated against the same current authorization and version constraints before generation and again before citation acceptance. Citations retain chunk/source IDs, content hash, title and locator. Existing session context uses bounded same-session user turns and never uses prior assistant text as factual evidence.

## Phase 09E runtime changes

The existing interpretation call remains the only conversational AI interpretation call. A new server-side query planner keeps the current business question, places an already-resolved contextual question first, and uses remaining slots for bounded provider-written alternatives. It sanitizes controls, bounds each query to 300 characters, deduplicates normalized whitespace/case variants, caps total queries at three, and rejects rewrites that introduce identifier-shaped values absent from the current or resolved context. Exact entities that passed the existing semantic validator are carried into accepted rewrites. The planner is advisory search text only: it cannot choose sources, capabilities, providers, or permissions. Mixed-scope requests plan only from the server-validated business span.

No new retrieval inference is added. The already configured optional embedding adapter still embeds only the first planned query in one existing request; all planned variants are used by the existing single lexical SQL query. With embeddings disabled or unavailable, retrieval remains lexical. Runtime authorization, citation validation, evidence revalidation and static/live limitations remain in place. The answer instruction now tells the provider to preserve separate source identities and disclose conflicting authorized sources with separate citations rather than silently merging them.

The SQL bound remains at 40 lexical candidates and at most the caller's 10 semantic/lexical result limit; the customer path selects at most five chunks and applies the existing evidence byte bound. No new cache, query loop, provider call, endpoint, schema or migration was added. The planner adds small in-process string validation and one structured log count (`rejectedExpansionCount`), with no query text logged.

## Evaluation coverage and limits

The existing versioned 09D.7 evaluation contract now has synthetic retrieval cases for English, Hinglish, Romanized Hindi, Hindi script, contextual follow-ups, multi-source facts, conflicting policies, absent/revoked/unlinked/private sources, citation integrity, exact IDs, static/live separation, document prompt injection, query bounds, dedup/ranking, embedding outage, and cross-tenant isolation. A deterministic query-plan check validates original-query retention, count/length/control bounds, and rejected-expansion count. Cases are fixtures and tests; no evaluation run or retrieval-quality score was produced.

## Confirmed gaps

- Multilingual vector search is available only when the opt-in embedding profile is configured and compatible vectors exist. Cross-lingual quality is not verified here; lexical PostgreSQL `simple` search is not a multilingual semantic substitute.
- No embedding threshold is applied. A top-ranked vector can still be weakly relevant; similarity/rank cannot prove evidence sufficiency or entailment. The system retains citation and response safety checks, but no semantic entailment judge is implemented.
- Contradictions are not deterministically detected. The generation instruction asks the provider to expose disagreements, but that behavior needs evaluation and is not a verified conflict detector.
- Current FAQ/Text chunking does not persist structural heading paths or page-section lineage. Existing chunk locator is the source name. Improving that lineage safely requires an index format change and reindexing, neither of which is performed in this phase.
- Website page ingestion/indexing is unavailable in the current Knowledge processing path, despite page and sync schema. It must be implemented separately before website sources can be claimed as searchable.
- `KnowledgeSource` freshness is protected through source version, active generation, READY state and repeated authorization revalidation. Freshness ranking is not introduced because timestamps do not establish factual currency for authored policies.

The next planned phase can proceed from these constraints; enabling embeddings or website indexing requires separately authorized configuration/infrastructure and should be assessed against reviewed retrieval cases before claiming quality gains.
