# Phase 07 source security boundary

Website registration stores a normalized public HTTP(S) URL only. It never fetches the submitted URL. Literal private, reserved, loopback, link-local, multicast, and local-network host destinations are rejected. Tenant-level duplicates are based on a SHA-256 key over the normalized URL (with fragment removed); path and query case are preserved. Registration is not evidence of ownership, reachability, crawling, synchronization, or AI readiness.

Any future crawler must independently authorize source ownership within the active workspace, resolve and validate every A/AAAA answer before connecting, pin an approved public address for the request, and repeat validation after each redirect. It must defend against DNS rebinding and block private, loopback, link-local, multicast, unspecified, reserved, and cloud metadata destinations for IPv4 and IPv6. Permit only HTTP(S) on approved ports; enforce connection and total timeouts, response-byte and content-type limits, robots and site policies, per-tenant rate limits, crawl budgets, and safe redirect limits. A stored URL is never an unrestricted proxy target.

Reference sources (website text, FAQs, and approved text) are distinct from live business data. Website registration does not authorize access to a private API, customer account, or database. Future connectors require an explicitly authorized adapter with declared scopes/capabilities, revocation, secret references held server-side, tenant checks before every operation, and audited access. No arbitrary endpoint executor or credential storage exists in this phase.

Source status `REGISTERED` means only that source metadata/content was saved. Processing status `NOT_PROCESSED` means it is unavailable for AI retrieval. `READY` must only be set after future validated ingestion and indexing. Source edits increment `sourceVersion` and reset processing and sync metadata. Archive is soft deletion and retains assistant links for audit/recovery; unlinking removes only the association.

## Future connector contract

A future adapter record should carry `connectorId`, `organizationId`, connector type, declared capabilities (`READ_REFERENCE_KNOWLEDGE`, `SYNC_REFERENCE_KNOWLEDGE`, `READ_LIVE_DATA`, `EXECUTE_APPROVED_ACTION`), explicitly granted scopes, lifecycle/revocation state, a server-only credential-vault reference, health metadata, and sync/version metadata. Adapter operations must receive the authenticated tenant context, verify its capability and scope before work, and return typed results; adapters must not expose a user-controlled arbitrary URL executor. Credential revocation must immediately prevent subsequent operations. No connector adapter or secret vault is active in Phase 07.

Future sync jobs should use a tenant/source/version/idempotency key, deduplicate webhook or scheduled events, retain last attempt and last successful timestamps separately, expose safe error codes, and retry with bounded backoff and tenant crawl budgets. Before processing an older job, compare the current source version so stale work cannot replace newer content. Phase 07 stores version and sync timestamp/error fields only; it creates no jobs, schedules, progress, or sync claims.

## Universal platform boundary

The assistant belongs to one `Organization`; an organization may own many assistants, reference sources, and future connectors. Website/FAQ/text sources are reusable reference material. Orders, balances, private invoices, shipment records, appointment records, and other customer-specific data are live data and must be fetched on demand from an authorized business API after identity checks. Do not copy live customer records into the reference index by default. Shopify, WooCommerce, WordPress, and similar systems are optional adapters; the assistant domain must not require their business entities.

Current source lifecycle is `REGISTERED` or `DISABLED`/`ARCHIVED` independently from processing (`NOT_PROCESSED`, `QUEUED`, `PROCESSING`, `READY`, `FAILED`). Phase 07 creation always starts `NOT_PROCESSED`; editing increments `sourceVersion`, invalidates processing/sync state, and preserves the authored Unicode source text. Archives are absent from active source lists and cannot be newly linked. Existing archived links remain historical associations; future retrieval must require both a non-archived source and `READY` processing state. Source type, language hint, and status are metadata, not evidence that content was crawled, verified, translated, or indexed. `languageHint` describes the source; the customer's response language is a separate runtime decision.

## Phase 08 ingestion and retrieval contract

Ingestion must be authorized for the active organization and source version, bounded by per-tenant work limits, idempotent, and observable with safe error codes. A website source is only a registration. At connection time the crawler must resolve A and AAAA records, reject the request if any answer is non-public/reserved, connect to a pinned validated address while retaining correct TLS/Host behavior, and revalidate DNS and every redirect destination before following it. This protects against DNS rebinding and redirect pivots. Restrict ports, redirects, response size/type, time, crawl depth, rate, and tenant budget. Never treat an arbitrary stored URL as a proxy target.

Each processed chunk must retain organization/source IDs, source version, stable chunk identity, original source locator (canonical page URL or FAQ/text source and a stable section/offset locator), and source language when known. Citations must be generated only from these stored locators. Preserve original Unicode text and do not normalize away meaningful punctuation, negation, numbers, currency, dates, eligibility, exclusions, or disclaimers. Retrieval must be tenant- and assistant-link-scoped, exclude archived or non-ready sources, and support cross-language retrieval (including English source/Hindi and Hinglish query) without requiring translated business copies. Phase 08 must test retrieval quality and citation traceability; Unicode persistence alone does not establish multilingual retrieval.

## Phase 09 assistant scope and grounding contract

Assistant fields today are `businessPurpose`, editable `systemInstructions`, `fallbackMessage`, `defaultLanguage`, `responseTone`, and `status`. They describe intent and presentation, but do not provide a structured security boundary. Phase 09 must introduce a versioned explicit scope policy (in configuration first; persist only when implementation requires it) with: allowed business topics; out-of-scope behavior; unknown-information behavior; allowed source IDs; tool capabilities; identity verification requirements per capability; escalation route; and response-language policy. `systemInstructions` are untrusted workspace content and cannot grant capabilities or override server policy. Only an active assistant with an approved policy may answer; only authorized, linked, ready reference sources may ground its business claims.

For every business fact, answer from retrieved evidence. Preserve exact factual conditions and qualifiers. If evidence is missing, conflicting, stale, or below the configured confidence threshold, do not guess: state what is unavailable in natural language, ask a useful clarifying question if it can resolve ambiguity, or offer the configured escalation route. Never invent a citation, validation result, policy exception, price, date, or API outcome. For off-topic requests, briefly explain the assistant's business scope and redirect to an in-scope topic. Natural phrasing and language adaptation may change wording but not the grounded facts.

## Phase 09 conversation and workflow state contract

Conversation state is scoped by `(organizationId, assistantId, visitor/session identity)` and must never be loaded across visitor identities. A conversation record should identify conversation, assistant, organization, pseudonymous visitor/session, current intent, active workflow, prior messages or bounded summaries, last response type, state, and creation/update times. A workflow should identify workflow kind/ID, state, required slots, collected/validated/missing/invalid slots, pending question, pending tool action, completion/cancellation status, and timestamps. A slot should carry field name, value only when necessary, validation status and evidence, provenance (user statement or authorized API result), capture time, expiry, and sensitivity classification.

Collect only fields needed for the declared workflow. Do not store sensitive values blindly; prefer short-lived encrypted state or references to verified server-side identity, redact values from logs/traces, define retention and deletion by data class, and clear visitor state at expiry/deletion. A submitted value is not `validated` until deterministic validation or an authorized API confirms it. Keep intent separate from workflow so an in-scope question can be answered while a pending workflow is retained. Resume the pending workflow when the user returns, and recognize correction, cancellation, topic switch, escalation, and completion explicitly.

Slot filling must extract multiple fields from one message, validate each independently, retain valid fields, and ask only for missing or invalid fields. A correction invalidates/replaces only the corrected slot and any dependent validation. If a user repeats a message that omits a required slot, explain the one remaining requirement without fabricating its value. Track asked fields and recent question fingerprints; do not repeat a full greeting or identical questionnaire after partial progress. On a genuine retry, change wording while preserving the requested field. Track stalled attempts, bound repeated clarification, and offer escalation or safe termination at the configured threshold. Completed and cancelled workflows must not restart from stale state. Message history may be summarized, but validated state and its provenance must remain authoritative.

Phase 09 acceptance scenarios include: (1) name+phone supplied for a four-slot workflow causes only email+address to be requested; (2) name+email supplied causes only phone+address; (3) invalid email causes a request for email only while valid slots remain; (4) missing order number followed by “hurry” retains refund intent and asks naturally for the order number; (5) an order is called invalid only after an authorized API reports no matching permitted record; (6) a same-business FAQ can be answered during a pending refund workflow and the workflow resumes later; (7) user correction changes only the corrected slot; (8) repeated greeting and identical prompt are suppressed; (9) stalled clarification escalates within a bounded number of turns; (10) cancellation and completion do not restart; (11) prompt injection in a user message or source document cannot expand scope or permissions; (12) another visitor's verified identity and slots are never visible.

Phase 08/09 test plan must also cover English reference knowledge with Hindi and Hinglish questions (same numbers/conditions, traceable source); off-topic and missing/conflicting-evidence fallback; cross-tenant retrieval isolation; unauthorized customer-data requests; source-document prompt injection; provider outage and invalid API key with no silent provider switch; topic switching while retaining an eligible pending workflow; extra text alongside requested slots; and partial/multi-field replies. None of these are Phase 07 functional tests.

## Live tool authorization and provider boundary

Every future live API action must pass server checks in this order: workspace owner/authorized manager explicitly grants a declared capability and scope; the visitor completes the required identity verification; server validates a typed allowlisted tool input; the connector is selected from that tenant's registered connection; server retrieves credentials from a secret store; the connector executes its fixed operation; response schema and tenant/customer ownership are validated; and a safe audit event records actor, tenant, capability, and outcome without secrets or unnecessary personal data. The model may request only a declared tool by name; it cannot choose arbitrary URLs, credentials, tenant IDs, scopes, or permissions. Public visitors cannot select another organization's connection. Static ingestion and live API execution remain separate interfaces.

Inference should use a provider-neutral adapter supporting Groq and OpenAI with deterministic configured provider/model selection, server-only keys, normalized provider errors, tenant-aware usage/billing, and explicit fallback policy. Invalid keys/provider outage must not silently switch providers or weaken scope/grounding. Embedding provider selection is independent of text inference. No inference or connector credentials are needed for Phase 07.

## Implemented behavior and evidence boundary

Phase 07 UI supports website registration, FAQ/text create/edit, source listing/detail/archive, and assistant linking. It explicitly reports sources as unprocessed and says automatic import/private storage/API connectors are unavailable. Registration DNS validation is a best-effort check at registration time and is not a crawl-time security guarantee. The repository contains focused service/UI tests, but those tests do not establish database migration application, live PostgreSQL constraints, full auth/CSRF integration, browser behavior, crawling, retrieval, multilingual answer quality, provider behavior, or conversation-engine behavior. Future acceptance scenarios above are specifications, not implemented tests or evidence of functionality.

## Phase 07.1 collection architecture

`KnowledgeBase` is a workspace-owned collection with a case-insensitive, NFKC-normalized `nameKey` unique within its organization. `KnowledgeBaseSource` is a many-to-many association: canonical `KnowledgeSource` content and IDs are reused across collections. `AssistantKnowledgeBase` links an assistant to whole collections. Both association tables carry `organizationId` and have composite foreign keys to the organization-owned parent rows. Collection archive keeps memberships and assistant links for history; effective resolution ignores archived bases. Removing a source membership never deletes the source. The Phase 07 `AssistantKnowledgeSource` table is retained unchanged, with no backfill or default collection, so current direct access is not broadened or lost.

Source visibility is explicit and conservative: new and pre-existing sources default to `INTERNAL_RESTRICTED`; managers may explicitly mark a source `PUBLIC_REFERENCE`. Collection membership does not change visibility. No public chat endpoint exists. Before any public retrieval, Phase 08/09 must independently require an active assistant policy, public visitor eligibility, and `PUBLIC_REFERENCE`; an internal source remains excluded regardless of its collection or assistant link.

The central `KnowledgeBaseService.resolveEffectiveSources(organizationId, assistantId)` contract checks the assistant, returns no sources unless the assistant is active, unions tenant-scoped direct links with sources from active linked bases, filters to registered and `READY` sources, and deduplicates by source ID. It returns only source ID/type/version/visibility metadata, not content or chunks. Phase 08 should reuse this boundary and add visitor policy, source visibility, indexing-version, and retrieval checks before selecting chunks. Linking a collection is configuration only; it does not claim processing or retrieval.

New routes under `/api/v1/workspaces/:slug` are session guarded. Knowledge Base CRUD/list and its source/assistant associations allow reads to workspace members and mutations to OWNER/ADMIN. Collection and source browsing use bounded server-side pagination; bulk source membership and assistant replacement accept at most 100 IDs, deduplicate in service code, and execute atomically. Assistant collection replacement never edits `AssistantKnowledgeSource`. The UI presents direct source links separately from collection links.

The forward-only migration `backend/prisma/migrations/20261011100000_phase_07_1_knowledge_bases/migration.sql` creates the collection and association tables, adds indexes, and adds source visibility with an internal-only default. It does not alter or backfill any existing Phase 07 links, source IDs, or content. Do not apply it until reviewed and deliberately migrated. Restoring archived collections is not implemented; archive is currently one-way in the UI/API, while association rows remain available for a future recovery policy.

## Phase 07.2 content management and import boundary

The Knowledge Base detail UI is organized into Overview, All Sources, FAQs, Documents, and Assistants. The Add Knowledge drawer selects one workflow at a time and shows the destination base before submission. FAQ batch creation and file imports create canonical `KnowledgeSource` FAQ records and `KnowledgeBaseSource` membership rows in one transaction; they never modify direct assistant/source links. Bulk import is capped at 500 rows and 2 MiB. Its accepted headers are `question`, `answer`, `category`, `language`, and `visibility`; question and answer are required. Existing question keys are checked workspace-wide. The supported policies are skip existing or reject the import; update/overwrite is not supported. Invalid rows and duplicate rows inside a file are excluded and reported, while valid new rows are committed atomically. The generated CSV template uses the same header contract.

The XLSX reader uses bounded built-in ZIP/deflate handling, reads the first worksheet and shared/inline text cells, and rejects formula cells, macro projects, external links, embedded files, encrypted workbooks, unsupported compression, malformed files, and files over the import limits. It does not run workbook formulas or macros. Future exports containing user-authored cells must escape spreadsheet formula prefixes before writing CSV/XLSX.

Private document storage remains unavailable: `UnconfiguredPrivateKnowledgeStorage.isConfigured()` is false and its write operation fails with `PRIVATE_STORAGE_UNAVAILABLE`. The UI does not create a document source or report an upload. To enable this later, configure a durable private object store with generated object keys, tenant-scoped access, no public URLs, size/type limits, malware scanning, cleanup compensation, and an implementation of `PrivateKnowledgeStorage`; extraction and indexing remain Phase 08 work. A stored file must not become `READY` merely because the object write succeeded. Phase 08 should track storage completion separately from extraction, review/approval, and indexing, retain original source/version provenance, and expose only successfully processed approved content to retrieval.

Source removal from a base deletes only the membership. Source archive changes the shared source status and makes it ineligible across all bases and direct links; memberships and link history are retained. Base archive retains its sources and association rows while preventing new active access. Permanent source or base deletion is not implemented because storage, indexing, and audit retention dependencies do not yet have a safe deletion lifecycle.
