# Phase 07 source security boundary

Website registration stores a normalized public HTTP(S) URL only. It never fetches the submitted URL. Literal private, reserved, loopback, link-local, multicast, and local-network host destinations are rejected. Tenant-level duplicates are based on a SHA-256 key over the normalized URL (with fragment removed); path and query case are preserved. Registration is not evidence of ownership, reachability, crawling, synchronization, or AI readiness.

Any future crawler must independently authorize source ownership within the active workspace, resolve and validate every A/AAAA answer before connecting, pin an approved public address for the request, and repeat validation after each redirect. It must defend against DNS rebinding and block private, loopback, link-local, multicast, unspecified, reserved, and cloud metadata destinations for IPv4 and IPv6. Permit only HTTP(S) on approved ports; enforce connection and total timeouts, response-byte and content-type limits, robots and site policies, per-tenant rate limits, crawl budgets, and safe redirect limits. A stored URL is never an unrestricted proxy target.

Reference sources (website text, FAQs, and approved text) are distinct from live business data. Website registration does not authorize access to a private API, customer account, or database. Future connectors require an explicitly authorized adapter with declared scopes/capabilities, revocation, secret references held server-side, tenant checks before every operation, and audited access. No arbitrary endpoint executor or credential storage exists in this phase.

Source status `REGISTERED` means only that source metadata/content was saved. Processing status `NOT_PROCESSED` means it is unavailable for AI retrieval. `READY` must only be set after future validated ingestion and indexing. Source edits increment `sourceVersion` and reset processing and sync metadata. Archive is soft deletion and retains assistant links for audit/recovery; unlinking removes only the association.

## Future connector contract

A future adapter record should carry `connectorId`, `organizationId`, connector type, declared capabilities (`READ_REFERENCE_KNOWLEDGE`, `SYNC_REFERENCE_KNOWLEDGE`, `READ_LIVE_DATA`, `EXECUTE_APPROVED_ACTION`), explicitly granted scopes, lifecycle/revocation state, a server-only credential-vault reference, health metadata, and sync/version metadata. Adapter operations must receive the authenticated tenant context, verify its capability and scope before work, and return typed results; adapters must not expose a user-controlled arbitrary URL executor. Credential revocation must immediately prevent subsequent operations. No connector adapter or secret vault is active in Phase 07.

Future sync jobs should use a tenant/source/version/idempotency key, deduplicate webhook or scheduled events, retain last attempt and last successful timestamps separately, expose safe error codes, and retry with bounded backoff and tenant crawl budgets. Before processing an older job, compare the current source version so stale work cannot replace newer content. Phase 07 stores version and sync timestamp/error fields only; it creates no jobs, schedules, progress, or sync claims.
