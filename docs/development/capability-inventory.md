# Current capability inventory

This inventory describes the current working tree on 2026-10-24. `SOURCE_IMPLEMENTED`, `PARTIALLY_IMPLEMENTED`, `NOT_IMPLEMENTED`, `DISABLED`, `CONFIGURATION_MISSING` and `SOURCE_DEFECT_FOUND` describe source/configuration evidence. `RUNTIME_PASS`, `RUNTIME_FAIL`, `RUNTIME_BLOCKED` and `NOT_TESTED` describe execution evidence independently. A source implementation is never a runtime PASS.

All runtime results below refer to deterministic unit/component/contract tests with mocked DB/HTTP boundaries. No row establishes deployed browser, real PostgreSQL, Shopify merchant data or paid-model success. Read the per-suite/per-assertion results and command ledger in [phase-00-verification.md](phase-00-verification.md). `RUNTIME_BLOCKED` also covers a suite that cannot reach its assertions because of a test compile/initialization failure. Partial suite failures must not be represented as every feature failing in production.

Source paths below are relative to the repository root. Backend workspace services are under `backend/src/modules/workspaces/`; browser clients are under `frontend/src/services/api/`. The verification ledger supplies the final executed status for each named suite. All 76 backend and 32 frontend baseline files now have completed assertion evidence; the consolidated red state is 116 backend and 85 frontend failed assertions. Earlier timeout/collection failures were rechecked and remain in their historical reports. RUNTIME_FAIL records at least one relevant failing test/contract; where mixed, inspect individual assertions before inferring the entire feature is broken. RUNTIME_PASS for recommendations and provider execution is limited to the exercised fixture boundary; live configuration, ranking/model quality and external connectivity remain unverified. NOT_TESTED rows have no sufficient assertion evidence for that exact operation.

## API contract boundaries inspected

| Browser operation | Backend method/path (under `/api/v1`) | Authorization / request / response boundary |
|---|---|---|
| Workspace get/list/members | GET `/workspaces/:slug`, `/workspaces`, `/:slug/members` | Session + active membership; lowercase role/currentUserRole; pagination |
| Assistant create/update/get | POST/PATCH/GET `/workspaces/:slug/assistants[/...id]` | Session + manager writes; Assistant DTOs; persisted assistant view |
| Playground chat/history | POST `.../:assistantId/playground/chat[/stream]`; GET `.../sessions/:sessionId` | Manager + owned session; bounded message/clientTurnId; reply/sources/provider/trace |
| Knowledge list/sync/status | GET `/workspaces/:slug/knowledge`; POST `.../:sourceId/website/sync`; GET `.../:sourceId/website` | Session + source access; source UUIDs and source/website DTOs |
| Knowledge Base/effective access | GET `/workspaces/:slug/knowledge-bases[/...id]`; GET `.../assistants/:assistantId/effective-knowledge` | Session + tenant/assistant access; paged source/base/effective access schemas |
| Shopify install/permissions | POST `/workspaces/:slug/connectors/shopify/install`; GET `.../connectors/:id/permissions` | Session + manager checks; shop-domain DTO; scopes and separate workspace/AI permissions |
| Products/details/orders | GET `/workspaces/:slug/products?externalId=...&integrationId=...`; GET `.../orders` | Session + permitted workspace data; CommerceListQueryDto; normalized record pages |
| Flow save/update/run | POST `/workspaces/:slug/flows`; PATCH `.../:flowId`; POST `.../:flowId/run` | Manager + same-tenant assistant; expectedVersion, graph validation, message/clientTurnId; graph/run trace |
| Widget configuration | GET/PATCH `/workspaces/:slug/widget` | Method-level AuthSessionGuard + manager service checks; domain/appearance DTO and persisted config |
| Public widget execution | POST `/widgets/bootstrap`, `/widgets/session/messages`; GET history | Exact origin and signed session token; does not use manager cookie to authorize visitor data |
| Conversation note | POST `/workspaces/:slug/conversations/:id/notes` | Session guard, workspace membership, OWNER/ADMIN permission; validated internal-note DTO; conversation tenant scope and audit entry |

The contract tests compare real clients and registered method/path/guard metadata, verify selected request bodies (`expectedVersion`, settings and messages), and preserve an actual owner response across the client boundary. The DTO and response schema tests in existing suites remain necessary: route matching alone does not prove DTO validation, service behavior or a deployed endpoint. HTTP mounting, real generated Prisma schema compatibility and live service connectivity remain unverified.
