# Carteio AI website widget

The production-ready Phase 13 embed asset is served at `/widget.js`. Workspace owners and admins configure it at Dashboard → Widget / Installation, save an assistant and approved domains, then copy the generated script tag. The script is technology-independent and uses a Shadow DOM; see the Phase 13 section in the root README for platform installation and API behavior.

The widget defaults its API origin to the origin that served `widget.js`; it never derives the API host from the storefront page. If the API is hosted separately, add `data-api-base-url="https://api.example.com"` to the script tag. The value must be an HTTPS origin; HTTP and loopback origins are accepted only when both the widget script and API origins are local development hosts.

The public widget API runs under `/api/v1/widgets/*`. Configure the existing private `AUTH_OTP_HASH_SECRET` with at least 32 bytes. Keep `TICKET_OUTBOX_WORKER_ENABLED=false` until migrations and the polling channel are verified in the target environment. No migration is applied by this repository implementation.

Widget bootstrap requires a browser `Origin` whose hostname exactly matches the single domain saved in that widget's configuration. Subdomains are not inherited: approving `example.com` does not approve `shop.example.com`; save the exact hostname that hosts the script. Production origins must use HTTPS. The development preview exception is limited to `localhost`, `*.localhost` and `127.0.0.1`, and each hostname must still be explicitly listed in the widget configuration; custom ports are accepted only for these local hosts. Missing Origin and unapproved domains are rejected. Referer is not used as a fallback. Origin/Referer headers are browser controls, not cryptographic proof: a non-browser client can forge them, so do not treat domain checks as protection against a malicious server that has copied the public widget ID.

The bootstrap access token is an HMAC-signed, widget-scoped session credential that expires after 15 minutes. Its claims contain a random session ID, public widget ID, approved-origin hash and expiry; tenant and conversation identifiers remain server-side. The database stores only a hash of the full token. Each protected request rechecks the signature, expiry, stored session, request Origin, current widget enablement, assistant status, approved domain and tenant-bound conversation. The separate resume credential is random, stored by hash and limited to the same widget, assistant, tenant, conversation and origin for up to 30 days. Disabling the widget or removing the domain prevents use immediately at the API authorization layer.

Widget CORS reflects an origin only when it matches a domain configured on an enabled widget. CORS is an additional browser boundary, never the authorization check; the API repeats the widget/session/domain checks for every protected action. The script uses Shadow DOM and does not create an iframe, so the website owner’s own `frame-src`/`script-src` policy controls whether the embed script can load.
